### 1. Introduction

This document outlines the requirements for a new feature to organize multi-agent reason trace files. Currently, trace files generated by multi-agent systems accumulate without a structured method for management, leading to difficulties in debugging, analysis, and storage management. This feature aims to provide users with tools to efficiently view, search, filter, group, and manage these trace files.

### 2. Feature Description

The "Multi-Agent Reason Trace File Organization" feature will provide a dedicated interface or set of functionalities for users to manage the output log/trace files generated by multi-agent simulations or real-world deployments. This includes capabilities to list, search, filter by various attributes, group into logical collections, add custom tags, and perform lifecycle management actions such as archiving and deletion. The goal is to enhance traceability, facilitate debugging, and improve overall system maintainability by imposing structure on potentially vast amounts of unstructured trace data.

### 3. User Personas

1.  **AI Researcher / Developer (Primary User)**
    *   **Goal:** Understand agent behavior, debug issues, validate hypotheses, optimize agent performance.
    *   **Needs:** Quick access to specific traces (e.g., failed runs, specific agents), ability to group traces by experiment, add notes, and analyze trace content.
    *   **Pain Point:** Sifting through hundreds or thousands of files manually, difficulty correlating traces to experiments.

2.  **System Operator / Administrator (Secondary User)**
    *   **Goal:** Ensure system health, manage storage, comply with data retention policies, provide traces for audits.
    *   **Needs:** Overview of storage consumption, ability to archive or delete old traces in bulk, monitor trace generation rates.
    *   **Pain Point:** Uncontrolled growth of trace files, manual clean-up is error-prone and time-consuming.

3.  **Data Scientist / Analyst (Tertiary User)**
    *   **Goal:** Aggregate trace data for higher-level insights, identify patterns, perform statistical analysis on agent interactions.
    *   **Needs:** Ability to export filtered sets of traces or trace metadata for offline processing.
    *   **Pain Point:** Difficult to select and extract relevant data from raw file dumps.

### 4. User Stories & Acceptance Criteria

#### 4.1. Core Functionality: Viewing & Searching

**User Story 1.1:** As an AI Researcher, I want to view a list of all multi-agent trace files so that I can understand what traces are available.
*   **Acceptance Criteria:**
    *   **AC 1.1.1:** The system shall display a paginated list of all trace files available to the user.
    *   **AC 1.1.2:** Each entry in the list shall, at minimum, display the file name, creation timestamp, file size, and the primary agent involved (if detectable).
    *   **AC 1.1.3:** The list shall be sortable by file name, creation timestamp, and file size (ascending/descending).
    *   **AC 1.1.4:** The user shall be able to click on a trace file entry to view its detailed metadata and potentially its content (as per existing trace viewer capabilities).

**User Story 1.2:** As an AI Researcher, I want to search for trace files by keywords (e.g., agent ID, experiment name, outcome) so that I can quickly find relevant debugging information.
*   **Acceptance Criteria:**
    *   **AC 1.2.1:** A search bar shall be present at the top of the trace file list.
    *   **AC 1.2.2:** Typing into the search bar shall dynamically filter the displayed list based on matches in file name, associated agent IDs, experiment IDs, or metadata keywords.
    *   **AC 1.2.3:** Search results shall highlight the matched keywords within the displayed trace file entries.
    *   **AC 1.2.4:** The search functionality shall support partial keyword matching.

**User Story 1.3:** As an AI Researcher, I want to filter trace files by specific attributes (e.g., agent ID, run status, experiment ID, date range) so that I can focus on specific problem areas.
*   **Acceptance Criteria:**
    *   **AC 1.3.1:** A set of filter options shall be available, including agent ID (dropdown/multi-select), experiment ID (dropdown/multi-select), run status (e.g., 'SUCCESS', 'FAILURE', 'IN_PROGRESS'), and a custom date range picker.
    *   **AC 1.3.2:** Applying one or more filters shall dynamically update the displayed trace file list to show only matching entries.
    *   **AC 1.3.3:** The system shall display the currently applied filters to the user.
    *   **AC 1.3.4:** The user shall be able to clear individual filters or all filters simultaneously.

#### 4.2. Organization & Management

**User Story 2.1:** As an AI Researcher, I want to group trace files into custom collections or 'experiments' so that I can manage related traces together.
*   **Acceptance Criteria:**
    *   **AC 2.1.1:** The user shall be able to select multiple trace files and assign them to an existing group or create a new group.
    *   **AC 2.1.2:** A new group creation shall require a unique name and an optional description.
    *   **AC 2.1.3:** The system shall display groups prominently (e.g., in a sidebar or as a top-level filter).
    *   **AC 2.1.4:** Viewing a group shall display only the trace files assigned to that group.
    *   **AC 2.1.5:** A trace file can belong to multiple groups.

**User Story 2.2:** As an AI Researcher, I want to add custom tags or labels to trace files so that I can categorize them according to my specific research needs.
*   **Acceptance Criteria:**
    *   **AC 2.2.1:** For each trace file, there shall be an option to add one or more custom tags.
    *   **AC 2.2.2:** Tags shall be free-form text inputs, with an option to select from previously used tags (autocomplete).
    *   **AC 2.2.3:** Tags shall be visible as part of the trace file's metadata in the list and detail views.
    *   **AC 2.2.4:** The system shall allow filtering or searching by tags.
    *   **AC 2.2.5:** The user shall be able to remove tags from a trace file.

#### 4.3. Lifecycle Management

**User Story 3.1:** As a System Operator, I want to archive old or completed trace files to cold storage so that I can manage disk space effectively.
*   **Acceptance Criteria:**
    *   **AC 3.1.1:** The system shall allow users with appropriate permissions to select one or more trace files and initiate an archiving process.
    *   **AC 3.1.2:** Archiving shall move the selected files from primary storage to a designated archival storage location (e.g., S3, Glacier, or a specified network share).
    *   **AC 3.1.3:** Archived files shall be clearly marked as 'Archived' in the UI and remain searchable and viewable, but potentially with slower access times.
    *   **AC 3.1.4:** A confirmation dialog shall be presented before archiving, detailing the number of files and the destination.
    *   **AC 3.1.5:** The system shall provide an option to retrieve archived files back to primary storage, subject to availability and access permissions.

**User Story 3.2:** As a System Operator, I want to delete trace files that are no longer needed so that I can free up storage resources.
*   **Acceptance Criteria:**
    *   **AC 3.2.1:** The system shall allow users with appropriate permissions to select one or more trace files and initiate a deletion process.
    *   **AC 3.2.2:** Deletion shall permanently remove the selected files from storage.
    *   **AC 3.2.3:** A prominent confirmation dialog shall be presented, warning of permanent deletion and requiring explicit user confirmation.
    *   **AC 3.2.4:** Deleted files shall no longer appear in any lists, search results, or groups.

**User Story 3.3:** As a Data Scientist, I want to export selected trace files or their metadata so that I can perform offline analysis.
*   **Acceptance Criteria:**
    *   **AC 3.3.1:** The system shall allow users to select one or more trace files for export.
    *   **AC 3.3.2:** The user shall be able to choose to export either the raw trace files or a structured metadata file (e.g., CSV, JSON) containing details of the selected traces.
    *   **AC 3.3.3:** The export process shall generate a downloadable archive (e.g., .zip) for raw files or a direct download for metadata.
    *   **AC 3.3.4:** The export shall respect existing access permissions.

### 5. Constraints

*   **Storage Integration:** Must integrate with existing file storage solutions (e.g., local disk, network share, cloud object storage).
*   **Performance:** The system must remain performant when handling tens of thousands (or potentially millions) of trace files. Search and filter operations must return results within a few seconds.
*   **Security:** Access to trace files and management actions (archive, delete) must adhere to existing role-based access control (RBAC) policies.
*   **File Format Agnostic:** The organization system should primarily manage the *files* themselves and their metadata, rather than requiring deep parsing of the specific trace file content format (though basic detection of key metadata like agent ID might be desirable).
*   **Existing Infrastructure:** Solution must be compatible with the current multi-agent system's logging and output pipeline, requiring minimal changes to how traces are initially generated.
*   **UI/UX:** The interface for organizing files should be intuitive and integrated into the existing platform's look and feel.

### 6. Edge Cases

*   **No Trace Files:** The system should gracefully display an empty state with clear instructions on how trace files are generated or where they should be placed.
*   **Corrupted Trace Files:** If a trace file is unreadable or corrupted, it should be flagged (if detected during metadata extraction) but not prevent the system from listing other files. Deletion/Archiving should still be possible.
*   **Large Number of Files:** Paginating results, optimized search indices, and asynchronous operations for bulk actions (archive/delete) are crucial to prevent timeouts or performance degradation.
*   **Permissions Denied:** If a user attempts an action (e.g., delete, archive) without sufficient permissions, an informative error message should be displayed, and the action prevented.
*   **Concurrent Modifications:** If multiple users attempt to modify the same trace file's metadata or group assignments concurrently, a robust conflict resolution or "last write wins" strategy should be implemented.
*   **Storage Full (Archiving):** If the designated archive storage is full or inaccessible, the archiving operation should fail gracefully, and the user should be notified. Original files should remain untouched.
*   **Search/Filter with No Results:** The system should clearly indicate that no results were found for the given criteria, rather than just showing an empty list.
*   **Invalid Input for Tags/Groups:** Input validation should prevent the creation of groups or tags with illegal characters or excessive length.
*   **Accidental Deletion:** The confirmation dialog (AC 3.2.3) is critical. Consideration for a "soft delete" or a temporary recycle bin might be explored in future iterations but is out of scope for V1.0.

### 7. Safety & Integration Notes

*   **Data Integrity:** Implement robust transactional mechanisms for archiving and deletion to ensure trace files are not lost or partially moved/deleted during an operation.
*   **Security & Access Control:**
    *   Strict RBAC must be applied to all management actions (archive, delete, create/manage groups).
    *   Ensure that trace file content itself is only accessible by authorized users, especially if traces contain sensitive information (e.g., PII, confidential research data). Data masking/redaction is out of scope but should be considered if traces contain PII.
*   **Performance Impact:** Monitor the impact of indexing, searching, and bulk operations on the underlying storage system and overall platform performance. Offload heavy processing if necessary.
*   **Integration with Multi-Agent System:**
    *   The system should ideally auto-discover trace files in configured directories or receive notifications from the multi-agent system upon trace generation.
    *   Consider standardizing trace file naming conventions or metadata injection at the source to facilitate easier organization.
*   **Audit Trail:** All lifecycle management actions (archive, delete, retrieve) must be logged for auditing purposes, including who performed the action and when (using the `2026-05-10 15:33:57 UTC` timestamp for consistency).
*   **Scalability:** The architecture should be designed to scale horizontally to accommodate a growing number of agents, experiments, and trace files over time.

If a user lacks `read` permission for a file, it must not appear in their list.

**Technical Details:**

*   **API Endpoints:**
    *   **Backend API:** `GET /api/v1/traces?page={int}&size={int}&sort_by={string}&sort_order={asc|desc}`
        *   **Parameters:**
            *   `page`: (Optional, default 0) Zero-indexed page number for pagination.
            *   `size`: (Optional, default 25) Number of trace file items per page. Maximum configurable size `N` to prevent excessive payload.
            *   `sort_by`: (Optional, default 'creation_timestamp') Field to sort results by (e.g., 'file_name', 'creation_timestamp', 'file_size_bytes', 'primary_agent_id').
            *   `sort_order`: (Optional, default 'desc' for `creation_timestamp`, 'asc' for others) Sort direction ('asc' for ascending, 'desc' for descending).
        *   **Response:** `200 OK` with a JSON payload containing:
            *   `items`: An array of `TraceFile` objects. Each object will minimally include: `id` (UUID), `file_name`, `creation_timestamp` (ISO 8601 UTC), `file_size_bytes`, and `primary_agent_id` (nullable string).
            *   `pagination`: Object containing `total_items`, `total_pages`, `current_page`, `page_size`.
*   **Data Model Changes:**
    *   A new `TraceFileMetadata` entity (or equivalent database table/document collection) is required to store trace file metadata. This entity will be managed by a dedicated service, separate from the primary multi-agent system.
        *   `id` (UUID, Primary Key, indexed)
        *   `file_path` (string, secure reference to the physical file location, e.g., `s3://bucket/path/to/file.log` or `/mount/path/file.log`. **Crucially, this path should not be directly exposed to the frontend without validation.**)
        *   `file_name` (string, indexed for searching/sorting)
        *   `creation_timestamp` (datetime, indexed for sorting)
        *   `file_size_bytes` (long, indexed for sorting)
        *   `primary_agent_id` (string, nullable, indexed, extracted during ingestion)
        *   `owner_user_id` (UUID, mandatory, foreign key to User entity, for RBAC enforcement)
        *   `associated_experiment_id` (UUID, nullable, for future grouping capabilities)
        *   `metadata_extract_status` (enum: 'PENDING', 'SUCCESS', 'FAILED')
        *   `last_modified_timestamp` (datetime, for internal tracking)
        *   `status` (enum: 'ACTIVE', 'ARCHIVED', 'DELETED', default 'ACTIVE', for lifecycle management)
*   **Backend Logic:**
    *   **Trace File Ingestion Service:** A microservice or background worker responsible for:
        *   Monitoring configured storage locations for new trace files.
        *   Extracting basic metadata (`file_name`, `creation_timestamp`, `file_size_bytes`).

        *   Persisting extracted metadata into the `TraceFileMetadata` data store.
        *   Handling potential failures during metadata extraction and marking files accordingly (`metadata_extract_status`).
    *   **Trace Metadata API Service:** Implements the `GET /api/v1/traces` endpoint.
        *   Queries the `TraceFileMetadata` store, applying RBAC filters based on the authenticated user's `owner_user_id` and potentially other access policies.
        *   Applies pagination and sorting parameters.
        *   Maps database entities to API response objects, ensuring no sensitive internal paths or data are exposed.
*   **Frontend Considerations:**
    *   A dedicated `TraceFileList` React/Vue/Angular component responsible for fetching data from the API and rendering the table.
    *   Robust error handling and display of user-friendly messages for API failures (e.g., network errors, permission denied).
    *   Interactive table headers for sorting, with visual cues for active sort.
    *   Pagination controls (buttons, current page indicator) that interact with the API.
    *   Loading spinners/skeletons for improved user experience during data fetch.
    *   Empty state illustration/message for "no traces found."
    *   Clickable rows/items that navigate to a `TraceFileDetails` route/component.
*   **Performance Considerations:**
    *   **Database Indexing:** Critical for all sortable columns (`creation_timestamp`, `file_name`, `file_size_bytes`, `primary_agent_id`) and `owner_user_id` for RBAC filtering.
    *   **Efficient Pagination:** Utilize database-specific pagination techniques (e.g., `OFFSET`/`LIMIT` or keyset pagination for very large datasets) to avoid full table scans.
    *   **Lazy Loading:** Only fetch and display data for the current page.

**Security Notes:**

*   **Role-Based Access Control (RBAC):**
    *   **Mandatory Enforcement:** The `GET /api/v1/traces` endpoint **MUST** strictly enforce RBAC checks on every request. Only `TraceFileMetadata` records for which the authenticated user has explicit `read` permissions shall be returned. This is the primary defense against unauthorized data disclosure.
    *   **Permissions Granularity:** RBAC should support permissions at the individual trace file level (via `owner_user_id`) and potentially broader group/project-level permissions.
    *   **Server-Side Filtering:** All RBAC filtering must happen on the backend. Never rely on client-side filtering for security.
*   **Input Validation & Sanitization:**
    *   All API query parameters (`page`, `size`, `sort_by`, `sort_order`) **MUST** be rigorously validated and sanitized on the server-side to prevent injection attacks (e.g., SQL injection) and ensure valid operations.
    *   `sort_by` values must be restricted to a predefined allow-list of safe, indexed columns.
*   **Data Minimization:**
    *   The API response for the list view should only include the necessary metadata fields (`id`, `file_name`, `creation_timestamp`, `file_size_bytes`, `primary_agent_id`). Avoid exposing internal system paths (`file_path`) or other sensitive operational details to the frontend or unauthorized users.
    *   No trace file content should ever be transmitted as part of the list view response.
*   **Transport Security:** All communication with the backend API **MUST** occur over HTTPS/TLS 1.2+ to protect data in transit from eavesdropping and tampering.
*   **Rate Limiting:** Implement API rate limiting on the `GET /api/v1/traces` endpoint to mitigate denial-of-service (DoS) attacks and prevent excessive resource consumption.
*   **Auditing:** Implement logging for all API requests to this endpoint, capturing user ID, timestamp, IP address, and request parameters. This provides an audit trail for access, which is especially important if trace files may contain sensitive research data or PII (as suggested in FR-005, Section 7).
*   **Secure Error Handling:** Suppress detailed technical error messages (e.g., stack traces, database errors) in API responses to avoid information leakage. Provide generic, user-friendly error messages.
*   **Least Privilege:** The backend service account interacting with the `TraceFileMetadata` database should operate with the principle of least privilege, having only the necessary permissions to perform its designated functions (e.g., `SELECT` on `TraceFileMetadata`).

def human_readable_size(size_bytes: int) -> str:
    """
    Converts a file size in bytes to a human-readable format (KB, MB, GB).
    Args:
        size_bytes: The file size in bytes.
    Returns:
        A string representing the human-readable file size, accurate to 2 decimal places.
    """
    if size_bytes < 0:
        return "N/A"
    if size_bytes == 0:
        return "0.00 B"

    # Define units and their corresponding powers of 1024
    units = ['B', 'KB', 'MB', 'GB', 'TB', 'PB', 'EB', 'ZB', 'YB']
    i = int(math.floor(math.log(size_bytes, 1024)))
    p = math.pow(1024, i)
    s = round(size_bytes / p, 2)
    return f"{s:.2f} {units[i]}"

    Manages access to trace file metadata, simulating database operations.
    Includes filtering, sorting, and pagination.

        self._db = db

    def get_trace_files(
        self,
        owner_user_id: uuid.UUID,
        page: int,
        size: int,
        sort_by: str,
        sort_order: Literal["asc", "desc"]
    ) -> Tuple[List[TraceFileMetadataDB], int]:
        """
        Retrieves a paginated and sorted list of trace files for a given user.
        Applies RBAC filtering.

        Args:
            owner_user_id: The ID of the user requesting the files (for RBAC).
            page: The zero-indexed page number.
            size: The number of items per page.
            sort_by: The field to sort the results by. Must be in ALLOWED_SORT_BY_FIELDS.
            sort_order: The sort direction ('asc' or 'desc').

        Returns:
            A tuple containing:
            - A list of TraceFileMetadataDB objects for the current page.
            - The total count of items matching the criteria (before pagination).

        Raises:
            ValueError: If sort_by is not in the ALLOWED_SORT_BY_FIELDS (should be caught by API validation).
        """
        # OWASP: A01: Broken Access Control - Server-side filtering by owner_user_id
        filtered_files = [f for f in self._db if f.owner_user_id == owner_user_id]

        total_items = len(filtered_files)

        # OWASP: A03: Injection - sort_by is validated by the API layer, but an extra check
        # here ensures robustness if this method is called internally.
        if sort_by not in ALLOWED_SORT_BY_FIELDS:
            logger.error(f"Attempted to sort by disallowed field: {sort_by} by user {owner_user_id}")
            raise ValueError(f"Invalid sort_by field: {sort_by}")

        # Sorting logic
        # For 'primary_agent_id', handle None values gracefully (e.g., treat None as lowest/highest)
        # Python's sort is stable and None comparison works, but explicit handling can be clearer.
        def get_sort_key(item: TraceFileMetadataDB):
            val = getattr(item, sort_by)
            if sort_by == 'primary_agent_id' and val is None:
                # Place None at the beginning for 'asc' and end for 'desc'
                return ("",) if sort_order == "asc" else ("\uffff",) # Use an empty string or max unicode char
            return val

        sorted_files = sorted(
            filtered_files,
            key=get_sort_key,
            reverse=(sort_order == "desc")
        )

        # Pagination logic
        start_index = page * size
        end_index = start_index + size
        paginated_files = sorted_files[start_index:end_index]

        logger.info(f"User {owner_user_id} fetched traces: page={page}, size={size}, sort_by={sort_by}, sort_order={sort_order}. Total found: {total_items}")

### Blockers

1.  **Dependency on Real RBAC System:** The current backend implementation relies on a mock `get_current_user` function. Integrating with the actual platform's production-ready Role-Based Access Control (RBAC) system is a critical dependency for deploying this feature to production and could present unforeseen complexities or delays.
2.  **Absence of Integrated Trace File Ingestion Service:** The `TraceMetadataRepository` currently uses mock data. The actual "Trace File Ingestion Service," responsible for monitoring storage locations, extracting real metadata from trace files, and populating the `TraceFileMetadata` database, is not yet implemented or integrated. This is a significant blocker for testing and operating the feature with live data.
3.  **Frontend UI Development & End-to-End QA Outstanding:** While the backend API is complete, the user story cannot be fully delivered to users without the corresponding frontend UI component. This means end-to-end user acceptance testing and full feature release are blocked until the frontend is developed and integrated.

1.  **Implement Automated Dependency Scanning:** To address the `A06: Vulnerable and Outdated Components` recommendation from the security audit, we should integrate automated dependency scanning tools into our CI/CD pipeline. This will proactively identify and alert us to security vulnerabilities in third-party libraries, ensuring our dependencies remain secure and up-to-date.
2.  **Formalize Integration Testing with Dependent Services:** Given the reliance on mock services (RBAC, Trace Ingestion), we need to formalize a strategy for robust integration testing. This includes defining clear test plans and allocating dedicated time and resources for testing the backend API's interaction with the *actual* RBAC system and the soon-to-be-developed Trace File Ingestion Service.
3.  **Standardize Production Deployment Configuration:** To mitigate `A05: Security Misconfiguration` issues identified in the audit (e.g., disabling `/docs` in production), we should develop a standardized, preferably automated, process for configuring services for different environments. This ensures that security-sensitive settings are correctly applied in production without manual intervention.
